# 맞춤 제안서 표준 목차와 절별 작성 규칙

분량 기준: 표지 포함 **12~18장**(세로형 슬라이드). 다음이면 7~10장 압축판(0·1·2·3·6·7·9장)으로:
대장만 있을 때(`ledger-only`), 리드 규모가 작을 때(50명 이하, 즉시 도입).
리드 폴더에 고객 요구사항·RFP·보안 점검표가 있으면 그 항목 순서를 2장 대응표의 순서로 쓴다.
RFP·입찰이면 RFP 목차가 우선이고, 아래 절은 그 안에 끼워 넣는다.

```
표지      고객사 귀중 / 제목(고객의 문제를 담은 명사구) / 부제 / 일자 · 클라우다이크 · 담당자
0. 한 장 요약
1. 고객 상황 이해          1-1 확인된 현황  1-2 촉발 사건과 목표  1-3 검토 관계자별 관심사
2. 요구사항 대응표          고객 원문 → 대응 → 근거 등급 → 절
3. 제안 구성               3-1 도입 형태·요금제  3-2 정책 설계안(설정값)  3-3 사용 구성도
4. 보안·통제               4-1 인증  4-2 통제·감사 항목  4-3 SaaS vs 구축형 비교 (요청 시)
5. 현행 대비 변화           현재 도구 vs 클라우다이크 (고객 요구 항목만)
6. 전환 계획               체험 → 계약 → 이관 → 전환, 단계별 통과 기준, 이관 소요 산정
7. 가격                   7-1 도입 견적  7-2 증설 시나리오  7-3 (해당 시) 바우처·3년 비교
8. 기대효과와 측정 방법
9. 확인 필요 사항과 다음 단계
별첨      A 약속 이행 대조표  B 인증서 사본(실물)  C 시연 영상 링크  D 출처
```

## 절별 규칙

### 표지 제목
제품명이 아니라 **고객의 문제를 해결한 상태**를 명사구로.
- 나쁨: 「클라우다이크 기업용 클라우드 제안서」
- 좋음: 「외부 협업 파일의 수명·권한 통제 체계 — 에이아이랩스 기업 드라이브 전환 제안」

### 0. 한 장 요약
고객 결정권자가 이 쪽만 읽는다고 가정한다.
- **핵심 제안 명제** 1단락 (`s.callout`): 촉발 사건 → 우리가 막는 구조 → 결과. 예:
  > 종료된 프로젝트의 외부 링크가 1년 뒤에도 열리는 문제는 직원의 주의가 아니라 **정책으로 닫혀야** 합니다. 클라우다이크는 외부 링크의 만료·비밀번호를 링크마다 걸고, 모든 열람·수정 이력을 사용자·파일별로 남깁니다.
- 숫자 카드 3개 표: 도입 규모 / 일정(계약·전환) / 첫해 금액(또는 [견적 협의])
- 미팅 약속 5가지가 어디 있는지 한 줄씩 → 고객이 "다 들어있다"를 30초 안에 확인

### 1. 고객 상황 이해
- **고객이 말한 사실만** 쓴다. 각 사실 끝에 출처를 단다. 고객 문서에 "리드 대장" 같은 내부 용어를 쓰지 말고
  「사전 상담(10/20 웹 데모 신청)」, 「10/25 미팅 [mm:ss]」처럼 고객이 기억하는 접점으로 표기한다.
- 회사 공개 정보(업종·규모)를 웹에서 찾았다면 출처와 함께 짧게. 못 찾았으면 쓰지 않는다 — 추정 업종 서술은 틀리면 치명적이다.
- 1-3 관계자별 관심사 표 → 각 행 끝에 "답하는 절" 열.

### 2. 요구사항 대응표
`references/lead-intake.md` 표 4 를 그대로. 근거 등급 열을 지우지 마라 — B 등급을 숨기면 나중에 기능 차이가 계약 분쟁이 된다.
고객용 문서에서는 등급을 「**기본 제공**」(A) / 「**시연 확인**」(B: 설명회·체험에서 화면으로 확인) 로 바꿔 쓰고, 요약 슬라이드 주석(`s.note`)에 두 표기의 뜻을 한 줄로 밝힌다.
"고객 원문" 열에는 **고객 발언만** 넣는다. 영업 담당자의 설명은 "대응" 열로.

### 3. 제안 구성
- 3-1: 형태(SaaS/공공/구축형) + 요금제 + 선택 근거 1~2문장. `quote.py` 결과와 일치시킨다.
- **3-2 정책 설계안이 이 제안서의 차별점이다.** 기능 나열 대신 "이 고객에게 이렇게 설정하겠다"는 설정값 표:
  | 정책 | 권장 설정 | 고객 요구 | 근거 |
  |---|---|---|---|
  | 외부 다운로드 링크 | 만료일 필수, 최대 30일, 비밀번호 필수 | R1 | A/B |
  | 파트너사 권한 | 읽기 전용(미리보기) 기본 | R3 | A/B |
  | 종료 프로젝트 | 콜드 아카이브 이동, 외부 링크 일괄 만료 | 촉발 사건 | A/B |
  기능은 모든 경쟁사가 비슷하게 주장한다. **고객 사건에 맞춘 설정값**은 우리만 쓸 수 있다.
- 3-3: 사용 구성도 — 사용자(탐색기·웹·모바일) / 외부 파트너(링크) / 관리자(정책·로그) 3주체. 그림이 없으면 표로.

### 4. 보안·통제 (보안팀이 읽는 절)
- 인증은 번호까지 (CSAP-2024-022). 등급·유효기간은 인증서로 확인 후.
- 통제 항목 표: 통제 / 동작 / 확인 방법(관리자 화면, 로그 추출) / 근거 등급.
- 고객이 구축형 비교를 원하면 4-3 에 SaaS vs 구축형 표 (저장 위치·과금·확장·연동·운영 주체·도입 기간). "구축형까진 필요 없을 것 같다"고 했다면 **권하지 말고 비교만** 한다.

### 5. 현행 대비 변화
`references/competitors.md` 원칙대로. 고객이 지금 쓰는 도구 1개 열 + 클라우다이크 1열, 행은 고객 요구 3~5개.
지금 도구의 장점(익숙함, 공동편집)도 한 줄 인정한다 — 공정해야 보안팀이 믿는다.

### 6. 전환 계획 (rnd-proposal 의 Stage-Gate 를 영업에 적용)
| 단계 | 기간 | 범위 | 통과 기준 | 고객 측 준비 |
|---|---|---|---|---|
| ① 체험 | 15일 | 연구팀 일부 N명 | 외부 링크 정책 시험, (확장 체험 환경 시) 대용량 업로드 재개 확인 | 체험 대상자 선정 |
| ② 보안 검토 | 1~2주 | 보안팀 설명회 | 통제 항목 체크리스트 승인 | 보안 점검표 공유 |
| ③ 계약 | — | | | 예산 품의 |
| ④ 이관 | 주말 | 10TB | 폴더·권한 샘플 대조 100% | 관리자 계정, 회선 |
| ⑤ 전환 | | 전 직원 | 1주 병행 후 기존 링크 차단 | 공지·교육 |
- **이관 소요를 산식으로** 쓴다 (`cloudike-facts.md` 7절). "주말에 끝납니다"를 회선 계산 없이 쓰지 않는다.
- 기존 도구의 외부 링크를 **언제 닫을지**를 반드시 쓴다 — 촉발 사건이 링크 문제였다면 이게 진짜 결과물이다.

### 7. 가격
- `scripts/quote.py` 출력 그대로. 공개 범위 초과는 `[견적 협의]`. **금액을 추정해 채우지 마라.**
  이때도 "공개 요금표 상한은 ENTERPRISE3(3TB, 연 10,335,600원)이며 귀사 규모는 맞춤 요금제 대상" 이라는 **기준점 한 줄**은 쓴다 — 고객이 금액의 자릿수를 가늠할 수 있다.
- 증설 시나리오: 고객이 말한 숫자(예: 180계정)만 쓴다. 용량 증가 숫자를 고객이 주지 않았으면 「현재 +50% / +100%」 두 단계를
  **예시**라고 밝혀 두고 단가는 `[영업팀 확정]`. 근거 없는 15TB·20TB 를 고객 숫자처럼 쓰지 마라.
- 계약 시점과 과금 시작 시점이 다르면(12월 계약·1월 전환) 과금 시작일을 `[영업팀 확정]` 으로 명시 — 고객의 "올해 예산 집행" 가능 여부가 여기서 갈린다.
- 사용자당 과금 대안과 비교할 땐 같은 인원·같은 기간(3년)·환율 기준일을 명시.
- VAT 별도 표기, 견적 유효기간 자리.

### 8. 기대효과와 측정 방법
정량 목표는 **측정 방법과 함께**만 쓴다 (rnd-proposal metrics 원칙).
| 지표 | 목표 | 측정 방법 | 시점 |
|---|---|---|---|
| 만료일 없는 외부 링크 | 0건 | 관리자 정책 + 링크 목록 점검 | 전환 후 30일 |
| 접근 이력 조회 소요 | 요청 당일 | 활동 로그 조회·추출 | 보안 점검 시 |
측정할 수 없는 효과("업무 효율 극대화")는 쓰지 않는다.

### 9. 확인 필요 사항과 다음 단계
rnd-proposal 의 「확인하지 못한 범위」 표를 영업용으로 쓴다. **못 확인한 것을 스스로 밝히면 신뢰가 오른다.**
| 항목 | 현재 상태 | 확인 방법·시점 |
|---|---|---|
| 다운로드 횟수 제한 | 미팅 설명, 공식 문서 미기재 | 체험 중 시연 |
| 관리자 링크 기간 강제 | 미팅 설명 | 보안팀 설명회에서 화면 시연 |
대장만으로 썼거나 「가정」이 있으면 이어서 **「첫 미팅에서 확인할 질문」** 표(질문 / 왜 묻는가 / 답에 따라 바뀌는 절)를 둔다.
그리고 다음 단계 3개(날짜·담당 포함)로 닫는다.

## 문체 규칙 (rnd-proposal 에서 승계)

- 제목은 문장이 아니라 **개념의 이름**(명사구). 「링크가 자동으로 닫힙니다」→「외부 링크 수명 정책」.
- 굵은 리드는 명사형 종결, 본문은 존댓말 평서형(`~합니다`). 고객 문서이므로 `~한다`체는 쓰지 않는다.
- 부정 단정으로 문단을 열지 않는다. 한 문장으로 잇고 **고객이 얻는 것**으로 닫는다.
- "최고의", "완벽한", "극대화" 금지. 숫자·설정값·절 번호로 말한다.
- 같은 내용은 한 곳에 쓰고 다른 곳에선 절 번호로 참조.
- 굵게는 한 단락에 1~2개.
- 고객사명·담당자명·직함 오탈자 0 — 대장 표기 그대로.

## 슬라이드 구성 (세로형 A4, `pptx_builder.py` 블록)

목차의 각 절을 아래 블록으로 옮긴다. **같은 블록을 연속 슬라이드에 반복하지 말고** 섞는다.

| 장 | 슬라이드 | 블록 |
|---|---|---|
| 표지 | 1장 | `deck.cover` |
| 0 한 장 요약 | 1장 | `callout`(제안 명제) → `stats`(규모·일정·첫해 금액) → `rows`(약속 5가지와 위치 — 한 줄짜리, 배지 없이) → `note`(배지 뜻) |
| 1 고객 상황 | 1~2장 | `rows`(확인된 현황, 출처) → `callout`(촉발 사건) → `cards` 2열(관계자별 관심사 → 답하는 장) |
| 2 요구 대응표 | 1~2장 | `table`(# / 고객 원문 / 대응 / 제공 배지, `badge_col`) — 8행 넘으면 나눈다 |
| 3 제안 구성 | 2장 | 3-1 `stats`+`cards`(형태·요금제·접속 환경) / 3-2 `table`(정책 설정값) + `cards` 3열(핵심 정책 3개) |
| 4 보안·통제 | 1~2장 | `cards`(인증·통제·로그, 배지) / 구축형 비교는 `table` 또는 `compare` |
| 5 현행 대비 | 1장 | `compare`(현재 도구 vs 클라우다이크) + `note`(출처·기준일) |
| 6 전환 계획 | 1~2장 | `steps`(단계·시점·내용·통과 기준) + `callout`(이관 소요 산식) |
| 7 가격 | 1장 | `stats`(첫해·증설) + `table`(시나리오, `[견적 협의]`) + `note`(VAT·유효기간) |
| 8 기대효과 | 1장 | `table`(지표/목표/측정 방법/시점) 또는 `cards` |
| 9 확인 필요·다음 단계 | 1~2장 | `table`(항목/상태/확인 방법, 배지) → `steps`(다음 단계 3개) |
| 별첨 | 필요한 만큼 | 약속 이행 대조표 `table`, 출처 `table` |

- 슬라이드 제목은 명사구, 22pt. `kicker` 에 `NN · 영문 라벨`(예: `03 · PROPOSAL`)로 장 번호를 관통시킨다.
- `lead` 는 그 슬라이드의 메시지를 한 문장으로. 제목이 주제, 리드가 주장이다.
- 빌더가 WARNING 을 내면 그 슬라이드를 나눈다. 글자 크기를 줄여 밀어 넣지 않는다.
- 발표용으로 쓸 수 있게 슬라이드마다 `s.notes()` 에 2~3문장 설명을 넣는다(선택).
