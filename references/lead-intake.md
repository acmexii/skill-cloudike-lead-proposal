# 리드 정보 해체 — 대장(필수) · 리드 폴더 자료(있으면)

제안서를 쓰기 전에 아래 다섯 가지 표를 먼저 만든다. RFP 가 없는 영업 제안에서는
**고객이 한 말과 영업 담당자가 약속한 말**이 RFP 역할을 한다. 그 말이 어디에 남아 있느냐에 따라 재료만 달라진다.

## 입력 읽기

- **리드 관리 대장(.xlsx/.csv) — 필수** : `python scripts/read_leads.py <파일> --company <고객사 일부>`
  Windows 에서 `python -I` 로 실행하면 PYTHONIOENCODING 이 무시되므로 스크립트가 직접 UTF-8 로 출력한다.
- **리드 폴더·관련 파일 — 있으면** : `python scripts/find_lead_materials.py <대장> --company <고객사명> --extract <작업폴더>/materials`
  권장 폴더 구조(사용자에게 안내할 때):
  ```
  <대장이 있는 폴더>/
    인바운드 영업 리드 관리 대장.xlsx
    에이아이랩스/            ← 폴더 이름에 고객사명만 들어 있으면 된다 ((주)·날짜 접두어 무관)
      녹취록_도입미팅_20261025.txt
      회의록_보안팀_20261105.docx
      고객메일_요구사항.pdf
      제안서_..._20261029.docx   ← 이 스킬이 저장한 이전 제안서도 다음 회차의 참조 자료가 된다
  ```
  대장 폴더 바로 아래에 `녹취록_에이아이랩스_….txt` 처럼 고객사명이 든 파일도 함께 잡힌다.

### 자료 유형별 읽는 법

| 유형 | 인용 방식 | 주의 |
|---|---|---|
| 녹취록(.txt/.vtt/.srt) | 고객 발언 원문 + `[mm:ss]` | 화자 구분: 고객 발언만 "고객 원문"으로 |
| 회의록(.docx/.md/.pdf) | 「11/5 회의록」 + 항목 번호·문장 | 회의록은 **요약**이다. 작성자의 해석일 수 있으니 결정사항·요청사항·후속조치 위주로 쓰고, 따옴표 인용은 회의록에 따옴표로 적힌 문장만 |
| 메일 | 「10/22 고객 메일」 + 문장 | 고객이 보낸 메일 = 고객 원문. 우리가 보낸 메일 = 약속 |
| 요구사항·RFP·보안 점검표 | 항목 번호 그대로 | **있으면 이것이 목차를 지배한다** — 항목마다 1:1 대응표(rnd-proposal 방식) |
| 기존 제안서·견적 | 이전 회차 번호·금액 | 이번 제안서와 숫자가 달라지면 변경 사유를 7장에 명시 |
| 메모 | 「영업 메모」 | 영업 담당자의 기록 — 고객 원문이 아니다 |
| 음성·영상만 | — | 전사본 없으면 사용 불가, 최종 보고에 "미반영 자료"로 |

## 대장만 있을 때 (`mode: ledger-only`)

녹취록·회의록이 없어도 제안서는 완성한다. 대장 한 줄은 생각보다 많은 것을 말해 준다.

| 대장 열 | 제안서에서의 쓰임 |
|---|---|
| 유입경로 · 문의일자 | 1장 "사전 상담(웹 데모 신청, 10/20)" — 고객이 기억하는 접점으로 표기 |
| 관심제품/솔루션 | 판매 형태 결정: "구축형/온프레미스/하이브리드" → 구축형 중심 + SaaS 비교, "스탠다드" → 해당 요금제, "+전자결재·API" → 연동 절(근거 B/C) |
| 도입규모(계정/용량) | `quote.py` 입력. 증설 시나리오는 「가정」 |
| 핵심요구사항/PainPoint | **고객 요구 대응표의 원문**. 문장 안의 요구를 쪼개 R1, R2… 로 (예: "유출 방지" / "접근 권한 이력 감사 리포트") |
| 도입예정시기 | 6장 일정 역산. "즉시" → 체험·계약을 압축, 날짜 → 그 날에서 역산 |
| 진행상태 | 문서 톤: 신규 접수 → 첫 제안(확인 질문 비중 큼), 상담 완료 → 구체 제안 |
| 후속조치(NextAction) | **약속 이행 대조표의 재료** (예: "방문 데모 시연 및 견적서 송부" → 견적 7장 + 시연 일정 제안 6장) |
| 비고 | 촉발 사건·검토 맥락 (예: "보안 가이드라인 준수 여부 사전 검토 요청" → 4장 보안 비중 확대) |
| 담당자 · 직책 | 관계자 표의 첫 행. 직책으로 관심사를 추정할 땐 「가정」 표시 (보안책임자 → 통제·감사, 마케팅 이사 → 공유 속도·대외 협업) |

원칙:
- **고객 발언을 지어내지 않는다.** 따옴표 인용은 대장 문구만, 출처는 「사전 상담 기록」.
- 대장으로 채울 수 없는 칸은 업종 일반론으로 메우지 말고 **「가정」** 배지를 달아 쓴다. 예: "외부 공유 대상은 연구 협력기관으로 가정(확인 필요)".
- 9장에 **「첫 미팅에서 확인할 질문」** 5~8개를 둔다. 가정 하나당 질문 하나가 원칙이다 — 가정이 질문으로 닫히면 제안서가 영업 도구가 된다.
- 촉발 사건이 없으면 표지·요약을 사건 대신 **대장의 PainPoint 문장**으로 연다.
- 분량은 압축판(6~9쪽)이 자연스럽다. 모르는 것을 길게 쓰면 신뢰가 떨어진다.

## 표 1. 리드 기본 정보 — 대장 vs 최신 기록의 차이

자료가 없으면 대장 값만 채우고 "확인·변경" 열은 「첫 미팅 확인」으로 둔다.

| 항목 | 대장 기록 | 최신 기록(녹취·회의록·메일)에서 확인·변경 | 제안서에 쓸 값 |
|---|---|---|---|
| 규모(계정/용량) | 150계정 / 10TB | 내년 상반기 180명 가능, 10TB 곧 초과 | 시작 150/10TB + 증설 시나리오 180 |
| 도입 시기 | 4분기 내 | 12월 초 계약(올해 예산), 1월 전환 | 계약·전환 분리 일정 |

**고객 접점 기록(녹취·회의록·메일)이 대장보다 최신이다.** 차이가 나면 최신 기록의 값을 쓰고, 대장 갱신이 필요하다고 마지막 보고에 적는다.

## 표 2. 촉발 사건 (왜 지금인가)

고객이 대체를 검토하게 된 **구체적 사건**을 한 문장으로 뽑는다. 제안서 첫 장의 주인공이다.
> 예: "지난달 보안 점검에서 1년 전 종료된 프로젝트 폴더 링크가 외부에서 아직 열리는 것이 발견되어, 보안팀이 대체 솔루션 검토를 지시함 [01:30]"

사건이 없으면 대장의 PainPoint 를 쓰되, "첫 미팅에서 확인할 것"으로 표시한다.

## 표 3. 의사결정 관계자와 각자의 질문

| 관계자 | 근거 | 이 사람이 제안서에서 찾을 것 |
|---|---|---|
| 현업 팀장(창구) | 미팅 참석 | 직원이 불편해하지 않는가, 예산 잡기 쉬운가 |
| 보안팀 | "보안팀이 그걸 제일 많이 물어봐요" | 링크 정책 강제, 접근 이력, 인증, 데이터 위치 |
| 재무·구매 | "올해 예산으로 집행" | 확정 금액, 증설 단가, 계약 시점 |
| IT·운영 | "10테라를 직원들이 직접 옮기라고 하면…" | 이관 방법·기간·중단 여부 |

제안서는 **이 사람들이 회의실에서 돌려 읽는 문서**다. 관계자마다 "자기 절"이 있어야 한다.
언급되지 않은 관계자를 지어내지 않는다.

## 표 4. 고객 요구 대응표 (= RFP 대비표)

고객이 말한 요구·질문을 **원문 그대로** 옮기고 대응을 붙인다. 요약해서 옮기면 고객이 "내 말이 반영됐나"를 확인할 수 없다.

| # | 고객 원문 (타임스탬프) | 대응 기능·방안 | 근거 등급 | 제안서 절 |
|---|---|---|---|---|
| R1 | "한 번 나간 링크가 언제까지 열려 있는지 관리가 안 됩니다" [01:19] | 다운로드 링크 만료일·비밀번호(A), 관리자 최대 기간 강제(B) | A/B | 3-2 |
| R2 | "누가 언제 어떤 파일을 열어봤는지 이력이 남나요?" [02:14] | 팀원별 활동 로그(A), 엑셀 추출(B) | A/B | 4-2 |

- 근거 등급은 `cloudike-facts.md` 기준(A 공개 확인 / B 영업 발언 / C 미확인).
- **대응 칸이 비면 본문을 쓰지 않는다.** 비는 칸은 "확인 필요 사항"으로 옮기고 이유를 쓴다.
- 대장의 `핵심요구사항`, `비고`, `후속조치` 칸도 요구로 본다 (예: "API 연동 문의", "NDA 체결").

## 표 5. 약속 이행 대조표

영업 담당자가 미팅에서 "제안서에 넣겠다 / 보내드리겠다"고 한 것을 **빠짐없이** 뽑는다.
녹취 끝의 요약 발언("오늘 내용을 정리해 보겠습니다…"), 회의록의 「후속조치·Action Item」, 우리가 보낸 메일의 약속 문장이 체크리스트다.
대장의 `후속조치(NextAction)` 칸도 약속으로 본다 — 자료가 대장뿐이면 이것이 대조표의 전부다.

| # | 약속 (원문, 타임스탬프) | 제안서 위치 | 상태 |
|---|---|---|---|
| P1 | "증설 단가를 제안서에 미리 명시" [00:46] | 7-2 | 단가 [영업팀 확정] 필요 |
| P3 | "대용량 이어 올리기 시연 영상" [04:07] | 별첨·메일 | 영상은 영업팀 준비 — 제안서엔 링크 자리 |
| P5 | "CSAP 인증서와 구축형 비교표" [04:07] | 4-1, 4-3, 별첨 | 인증서 사본 실물 첨부 필요 |

상태가 "준비됨"이 아닌 항목은 최종 보고에서 **사람이 채울 것** 목록으로 올린다.
약속 하나라도 빠지면 고객은 "듣지 않았다"고 읽는다 — 영업 제안서에서 가장 치명적인 감점이다.

## 영업 담당자 발언의 기능 주장 처리

녹취·회의록·메일 속 영업 담당자의 기능 설명(예: "다운로드 횟수를 지정할 수 있고요")은 **고객에게 이미 한 약속**이다.
- 공식 페이지로 확인되면 A — 그대로 쓴다.
- 확인 안 되면 B — 본문에는 쓰되(이미 말한 것을 빼면 고객이 의아해한다) 「확인 필요 사항」 표에 "제품팀 확인 후 발송"으로 올린다.
- 공식 자료와 **모순**되면 쓰지 말고 최종 보고 맨 위에 경고한다.

## 일정 역산

고객이 준 날짜(제안서 송부일, 계약 희망일, 전환 희망일, 체험 기간)를 한 줄 타임라인으로 만든다.
> 10/29 제안서 송부 → 11월 15일 체험(연구팀 일부) → 보안팀 설명회 → 12월 초 계약 → 1월 주말 이관·전환

날짜 사이에 **누가 무엇을 해야 다음 단계로 넘어가는지**(통과 기준)를 붙이면 6장 전환 계획이 된다.
